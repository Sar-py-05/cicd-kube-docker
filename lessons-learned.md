# Lessons Learned

## Project

**End-to-End CI/CD Pipeline using Jenkins, Docker, SonarQube, DockerHub, Helm, KOPS and Kubernetes on AWS**

---

# Overview

This project provided hands-on experience in building a production-style CI/CD pipeline for deploying a Java application to a Kubernetes cluster. Beyond implementing the pipeline, the project involved diagnosing and resolving numerous real-world issues related to Jenkins, Docker, SonarQube, Kubernetes, Helm, Git, Java, and AWS.

The following are the key technical lessons learned throughout the project.

---

# 1. CI/CD is More Than Writing a Jenkinsfile

Initially, the focus was on creating a Jenkins pipeline. During implementation, it became clear that a successful CI/CD process depends on multiple interconnected systems working together.

A complete pipeline requires:

- Source Code Management
- Build Automation
- Code Quality Analysis
- Containerization
- Container Registry
- Kubernetes
- Helm
- Infrastructure
- Networking
- Security
- Monitoring

A failure in any component can stop the deployment.

---

# 2. Tool Version Compatibility Is Critical

One of the biggest lessons was understanding how important version compatibility is across the entire DevOps toolchain.

Examples encountered during this project included:

- Jenkins requiring Java 17 or later for agents.
- Docker images using deprecated base images.
- Helm versions differing across servers.
- Maven and JDK compatibility.
- Kubernetes API version compatibility.

Version mismatches often caused failures that initially appeared unrelated.

---

# 3. Jenkins Global Tool Configuration Must Match the Jenkinsfile

The pipeline failed because the Maven tool name in the Jenkinsfile did not exactly match the configured tool name in Jenkins.

Example:

Incorrect:

```groovy
maven "maven3.9.9"
```

Correct:

```groovy
maven "MAVEN3.9.9"
```

This reinforced the importance of keeping Jenkins Global Tool Configuration synchronized with pipeline code.

---

# 4. Jenkins Agents Require Modern Java

The KOPS Jenkins agent failed to launch because it was running Java 8, while the Jenkins Remoting JAR required Java 17 or newer.

Error:

```
UnsupportedClassVersionError
```

After upgrading the agent to Java 21, the connection succeeded immediately.

Lesson:

Always verify Java versions on every Jenkins node, not just the controller.

---

# 5. SonarQube Quality Gates Should Match the Project Stage

The SonarQube scan completed successfully, but the pipeline failed because the Quality Gate returned `ERROR`.

For a training environment, the pipeline was configured to continue despite a failed Quality Gate.

For production environments:

- Quality Gates should be enforced.
- Deployments should stop when code quality standards are not met.

This highlighted the balance between learning workflows and production best practices.

---

# 6. Docker Base Images Can Become Obsolete

The original Dockerfile referenced:

```dockerfile
FROM openjdk:11
```

The image was no longer available, causing Docker builds to fail.

The solution was to use actively maintained images:

```dockerfile
FROM eclipse-temurin:21-jdk
FROM tomcat:9.0-jdk21-temurin
```

Lesson:

Always verify Docker base images and keep them updated.

---

# 7. Keep Dockerfiles Simple

The original Dockerfile cloned a Git repository and built the application inside the image.

This approach introduced unnecessary dependencies and slowed the build.

The improved Dockerfile simply copied the already-built WAR file generated by Jenkins.

Benefits:

- Faster builds
- Smaller images
- Better separation of responsibilities
- Easier troubleshooting

---

# 8. Personal Access Tokens Are the Standard for GitHub

GitHub no longer accepts account passwords for Git operations.

The project required using:

- Personal Access Tokens (HTTPS)
- SSH keys

Lesson:

Always configure secure authentication methods before automating Git operations.

---

# 9. DockerHub Authentication in Jenkins

A common misconception was that the Google account password used to sign in to DockerHub should be used in Jenkins.

The correct approach is to use:

- DockerHub username
- DockerHub password (or access token if enabled)

Stored securely as a Jenkins credential.

---

# 10. Helm Simplifies Kubernetes Deployments

Instead of manually applying multiple YAML files, Helm allowed the entire application to be deployed or upgraded with a single command.

Example:

```bash
helm upgrade --install vprofile-stack \
helm/vprofilecharts \
--namespace prod \
--create-namespace
```

Benefits:

- Versioning
- Rollbacks
- Reusable templates
- Parameterized deployments

---

# 11. Validate the Cluster Before Deploying

Before every deployment, the cluster was validated using:

```bash
kops validate cluster
```

This simple step prevents deployments to unhealthy clusters.

Lesson:

Infrastructure validation should always precede application deployment.

---

# 12. Jenkins Credentials Improve Security

Sensitive information such as:

- DockerHub credentials
- SonarQube tokens
- GitHub Personal Access Tokens
- SSH private keys

were stored in Jenkins Credentials rather than hardcoded into the pipeline.

Lesson:

Never store secrets in source code.

---

# 13. Infrastructure Issues Can Break the Pipeline

Several failures were caused by infrastructure rather than application code.

Examples included:

- Docker repository conflicts
- Network timeouts during package installation
- Security group misconfigurations
- Offline Jenkins agents
- Java version mismatches

Lesson:

Successful CI/CD depends on reliable infrastructure.

---

# 14. Incremental Testing Saves Time

Rather than troubleshooting the entire pipeline at once, each stage was validated independently.

Sequence:

1. Maven Build
2. Unit Tests
3. Integration Tests
4. Checkstyle
5. SonarQube
6. Docker Build
7. Docker Push
8. Helm Deployment

This approach isolated issues quickly and reduced debugging time.

---

# 15. Logging Is Essential

Detailed Jenkins console logs were invaluable for diagnosing failures.

Examples:

- Maven errors
- Docker build failures
- SonarQube analysis
- Helm deployment status
- Kubernetes rollout progress

Lesson:

Always examine logs before making changes.

---

# 16. Kubernetes Is Self-Healing

Deleting a pod demonstrated Kubernetes' self-healing capability.

```bash
kubectl delete pod <pod-name>
```

The Deployment automatically created a replacement pod.

This reinforced the value of declarative infrastructure.

---

# 17. Helm Rollbacks Provide Operational Safety

Helm's release history made it possible to revert deployments quickly.

Commands:

```bash
helm history vprofile-stack
```

```bash
helm rollback vprofile-stack <revision>
```

Lesson:

Rollback capability is a key operational advantage of Helm.

# 20. Small Configuration Errors Can Cause Large Failures

Several pipeline failures were traced back to small mistakes, including:

- Incorrect tool names
- Typographical errors
- Wrong image tags
- Invalid credential IDs
- Missing Helm release names
- Incorrect Java versions

Lesson:

Carefully review configuration files before assuming complex root causes.

# Overall Project Outcome

By the end of the project, a fully functional CI/CD pipeline was implemented with the following capabilities:

- Source code retrieved automatically from GitHub.
- Maven build, unit tests, integration tests, and Checkstyle executed successfully.
- SonarQube analysis integrated into the pipeline.
- Docker image built using a modern multi-stage Dockerfile.
- Versioned and latest Docker images published to DockerHub.
- Local Docker images cleaned up after successful pushes.
- Jenkins SSH agent configured on the KOPS management server.
- Helm deployed the latest application image into the Kubernetes `prod` namespace.
- Kubernetes performed rolling updates with the new application version.
- The entire pipeline completed successfully from code commit to Kubernetes deployment.

This project demonstrated that modern DevOps is much more than automating deployments. It requires a solid understanding of software development, infrastructure, networking, containerization, security, orchestration, automation, and operational troubleshooting.

Successfully completing this project significantly strengthened practical skills in building and maintaining production-style CI/CD pipelines on AWS using Jenkins, Docker, SonarQube, Helm, KOPS, and Kubernetes.
